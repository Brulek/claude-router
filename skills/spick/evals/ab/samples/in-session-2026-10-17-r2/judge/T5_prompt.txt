=== 回答 B ===
每日备份方案（设计）

一、备份范围
- 代码：~/dev/ 各项目。git 仓库以 GitHub 私有远端为异地副本，每日把未推送的提交与分支推上去；未跟踪文件与 stash 另行打包。
- 文稿：~/Documents 经 iCloud 同步，但同步会传播误删，需另做日快照。
- 配置：~/.claude、~/claude-sync、钥匙串导出（加密后单独存放）。
- Windows：用户目录与其项目目录。

二、频率
- 代码推送与文稿快照每日一次（夜间）；配置每周一次。
- 快照保留：近 30 天日快照，12 个月月快照。

三、存储位置
- 本地：各 Mac 的 Time Machine 或外置盘；Windows 用文件历史。
- 集中：一台 NAS，每日汇总各机快照。
- 异地：加密后上传云对象存储，每周一次。

四、恢复演练
- 每月一次：从远端克隆一个项目，并从快照还原一个文件，记录耗时与结果。
- 每季度一次：整机或虚拟机恢复演练。
- 演练失败即视为方案失效，先修复再继续。

五、风险与取舍
- iCloud 不是备份，误删与冲突会被同步到所有机器。
- 加密密钥丢失则备份全部作废，需离线保存两份。
- 全量上传占用带宽与费用，采用增量与去重。
- 凭据备份范围越小越安全，钥匙串条目逐一评估。
- 三平台工具不统一会增加维护成本，建议统一用一种备份工具（如 restic）。

=== 回答 C ===
**备份范围**：① ~/dev 全部仓库的未提交改动、stash 与忽略文件（排除 node_modules、构建产物）；② ~/Documents 中非可再生资料；③ ~/claude-sync 等 Claude 配置；④ Windows 机器上的项目目录。代码以 Git 远端为准，备份只补远端没有的内容。

**频率**：每日夜间增量备份一次；代码每次提交后推送 GitHub 私有远端；每周一次全量快照。

**存储位置**：遵循 3-2-1 原则。本地一份（外置盘或 NAS）、另一种介质一份（Time Machine 或另一台机器）、异地加密一份（如 Backblaze B2）。Mac 与 Windows 统一用 restic。iCloud 不作为备份，因其会损坏 Git 仓库。

**恢复演练**：每月随机抽一个项目还原到临时目录，执行 git status 与测试；每季度模拟一次整机恢复，记录耗时与缺口。

**风险与取舍**：
1. 加密口令丢失则备份全部不可用，口令需离线双份保存。
2. 勒索软件可能同步破坏云端备份，需保留多版本或不可变快照。
3. 夜间任务依赖开机，错过则次日补跑。
4. 全量备份占空间，靠去重控制成本。
5. 钥匙串与 API 密钥不进普通备份，单独加密保管。
