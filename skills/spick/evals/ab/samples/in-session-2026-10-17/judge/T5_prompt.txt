=== 回答 X ===
**统一每日备份方案(3-2-1 原则)**

**一、备份范围**
- 必备份:~/dev 下各项目的未推送工作(git 仓库本身以 GitHub 远端为主副本,另备份整个目录的 .git 与未跟踪文件);文稿目录(含各类资料、脚本、产出);Claude/工具配置(~/.claude、~/claude-sync、himalaya 配置等);各机应用配置(Clash、shell 配置、SSH 公私钥)。
- 排除:node_modules、target、DerivedData、.venv、缓存、系统与应用本体。这些可重建,备份会使体积膨胀数十倍。
- 敏感项:钥匙串、授权码、API key 不明文备份。只导出清单(条目名与用途),并把恢复步骤记在密码管理器里。

**二、频率**
- 每日一次增量备份,夜间触发。笔记本合盖或离线则下次联网时补跑。
- 设置每台机器的成功时间戳,超过 36 小时未成功就通知提醒。
- 重大操作(大规模重构、迁移目录)之前手动加跑一次。

**三、存储位置(三层)**
1. 本机层:Mac 用 Time Machine 备份到外接 SSD,Windows 用文件历史记录。它们保障快速回滚,保留 30 天。
2. 异地层:用 restic 或 Kopia 做去重加密快照,统一推送到同一个云对象存储(如 Backblaze B2 或 Cloudflare R2)。它跨 macOS 和 Windows,每台机器各建一个仓库,密码由用户自行保管。保留策略为日 14、周 8、月 12。
3. 代码层:所有 ~/dev 项目保持 GitHub 私有仓库推送。每日脚本检查"本地有未推送提交或未提交改动"的仓库并告警。

**四、关键约束**
- 不要把 git 仓库放进 iCloud(会损坏仓库)。文稿目录虽经 iCloud 同步,但同步不是备份:误删与冲突会同步扩散,所以文稿目录仍需独立快照。
- 备份源用只读快照(APFS 快照或 VSS),避免备份时文件正被写入。

**五、恢复演练**
- 每月:随机抽取一台机器,从云端恢复一个项目目录和一份文稿到临时路径,比对校验和,并记录耗时。
- 每季度:模拟整机丢失,在空白环境从零恢复 ~/dev、文稿与配置,验证钥匙串条目清单足以重建登录与授权。
- 每次演练的结果写进一份简短日志。失败项当场修复,并重新计时。

**六、风险与取舍**
- 加密密码丢失,云端备份即全部作废。对策是把密码存在密码管理器,并在纸质或离线介质上留一份。
- 云存储持续产生费用,体积主要取决于图片和安装包。对策是排除可重建内容,并按月核对账单。
- 只靠 iCloud 或只靠 GitHub 都不足。前者会同步误删,后者覆盖不了未提交内容和非代码资料。
- Windows 与 macOS 路径、权限、大小写规则不同,恢复到异系统时可能出错。对策是每台机器各用独立仓库,并在恢复演练中覆盖跨系统读取。
- 取舍:统一用一套工具(restic/Kopia)会牺牲每个系统的原生体验,但维护成本低、演练流程一致。对小规模个人环境,这比多套原生方案更可靠。
- 每日备份最多丢失约 24 小时的数据。如果某个项目在高强度开发中,就提高该项目的提交与推送频率,不必缩短全局备份间隔。

- iCloud 与 git 双重同步会损坏仓库，所以备份工具只读源目录，仓库不放在 iCloud 内。
